# Design: Two-door house brain

Generated by /office-hours on 2026-11-12

## Problem Statement

Each AI client of the builder has its own memory or none. Claude Code has memory files. Claude Desktop, Cursor and the Claude phone app have nothing shared. A fact that one client learns is not available to the others.

`open_brain` already gives one shared memory to all MCP clients on one computer. It uses stdio only, so a phone can not connect to it. It has no sign-in, no scope filter and no exact-string search.

The builder wants one memory for all clients, on the PC and on the phone, with house facts as the first content.

## What Makes This Cool

You stand in a hardware store. You ask the Claude phone app for the size of the furnace filter. The answer comes from a note that you gave to Claude Code on your PC three weeks before. The database that holds the note is on your own home server.

## Constraints

- One user. Family access is out of scope.
- Data boundary: the stored database and the embeddings stay at rest on the home server. No embedding provider in the cloud sees a note. A tool result that a client requests goes to that client. A tool input (a captured fact or a search query) comes from that client. For the phone and for each cloud client, the tool inputs and the tool results go through the Anthropic cloud. The builder must approve this boundary.
- The repository is public. No personal configuration, host name, address or note goes into git.
- The work goes to a fork that the builder owns. A pull request to the upstream repository is optional.
- Claude custom connectors connect from the Anthropic cloud, not from the device. The server must have a public HTTPS address for the phone. Source: Claude help center, read on 2026-11-12. Not tested live.
- Do not run `npm run init-db` or change a database without approval (rule from `AGENTS.md`).

## Premises

1. Extend `open_brain` in a fork. Do not adopt a ready memory server. Why: the goal is to learn, and the codebase is about 500 lines.
2. The hard part is the public door, not the memory. The public door opens with read-only tools. Write tools go public only after the sign-in passes a probe. (Revised after the second opinion.)
3. Postgres with pgvector and Ollama `nomic-embed-text` (768 dimensions) run on the home server. The schema records the embedding model of each row and has a full-text column. (Revised.)
4. One table, one user. Search takes a `scope` filter. A tag alone is not sufficient. (Revised.)
5. Public repository boundary: configuration stays in ignored files.

## Cross-Model Perspective

A Claude subagent with fresh context read a summary of the session. It is the same model family, so its agreement has less weight than an outside model. It did not test a connector or a tunnel.

- Coolest version: a brain that fills itself. A nightly job writes events from the chores app and the recipe server into the brain as dated facts.
- Key quote: "one memory for all tools and house brain". Its view: the house is the fun part, and the first milestone must not be only plumbing.
- Existing 50%: the MCP TypeScript SDK in `package.json` has `StreamableHTTPServerTransport` and OAuth helpers. Do not write an authorization server by hand.
- Disputed premise 2 (High): write tools on the public internet on day one permit memory poisoning after one sign-in mistake. Accepted.
- Disputed premise 4 (Medium): a tag does not stop house facts in work answers. Accepted.
- Disputed premise 3 (Medium): the model is fixed in the column type, and vector search misses strings such as `20x25x1`. Accepted in part. Ollama stays.
- Backup (Low): a backup is not proven until one restore succeeds. Accepted.

## Approaches Considered

### Approach A: One door

One public endpoint for all devices. Rejected: PC capture must wait for the sign-in, and the builder must own an authorization server.

### Approach B: Two doors (chosen)

One server process with two listeners. See Recommended Approach.

### Approach C: House first

Private door only, plus a nightly job that fills the brain from the chores app and the recipe server. Rejected as the first step because it has no phone access. It stays as a later phase.

## Recommended Approach

### Structure

One Node process on the home server starts two HTTP listeners. Each listener has its own tool set.

Each door runs the transport in stateless mode. The server makes a new `McpServer` and a new transport for each request, so two clients on one door do not share state.

| Door | Container port | Published on the host | Access control | Tools |
|---|---|---|---|---|
| Private | 8787 | Tailnet address of the home server only | Tailscale | All 5 tools |
| Public | 8788 | `127.0.0.1` only; the tunnel on the host sends requests to it | OAuth 2.0 bearer token | Read-only first: `search_brain`, `list_recent`, `brain_stats` |

Stdio stays as a third mode for local development.

### Network

- In the container, each listener binds `0.0.0.0` on its own port. The container is on the default bridge network.
- Compose publishes port 8787 as `${TAILNET_IP}:8787:8787` and port 8788 as `127.0.0.1:8788:8788`. `TAILNET_IP` comes from the ignored `.env` file.
- The tunnel runs on the host, not in Compose, and sends public requests to `127.0.0.1:8788`.
- If Tailscale is not ready when Docker starts, the publish of port 8787 fails and Docker does not start the container again. A restart policy applies only after a successful start. For this reason a small systemd unit on the host starts the stack. The unit runs after `tailscaled`, waits until the tailnet address exists, then runs `docker compose up -d`.
- Check in Phase 1: a request to port 8787 on the LAN address of the home server gets no connection. A request to port 8788 from a different machine gets no connection.
- Reboot check in Phase 1: after a reboot of the home server, the private door answers with no manual work.
- Reboot check in Phase 2: after a reboot, the tunnel and the public door also answer with no manual work.
- The unit file is in the repository as `deploy/open-brain.service.example`. It has placeholder values and no host name or address. The unit waits a maximum of 120 seconds for the tailnet address. If the address does not come, the unit fails, and `Restart=on-failure` with a delay of 30 seconds starts it again.
- Only the `open_brain` service publishes ports. The Postgres port and the Ollama port stay unpublished.

### Code changes

- New `src/tools.ts`: a function `registerTools(server, { tools, allowSupersede })` holds the 5 tool handlers that are in `src/index.ts` today. `tools` is the list of tool names to register. `allowSupersede` controls the `supersedes` parameter of `capture_thought`.
- The three tool sets are: private door, 5 tools with `allowSupersede: true`; public door in Phase 2, the 3 read tools; public door in Phase 3, the 3 read tools plus `capture_thought` with `allowSupersede: false`.
- `src/index.ts`: reads the mode from the environment (`stdio`, or HTTP) and starts the listeners. It uses `StreamableHTTPServerTransport` from the SDK that is already a dependency.
- New `src/auth.ts`: token check for the public door. See Sign-in.
- `src/db.ts`: `searchThoughts` takes a `scope` and does hybrid search. `insertThought` takes `scope`, `embedding_model` and an optional `supersedes` id.
- `src/embeddings.ts`: exports the name of the active model so that `insertThought` can record it. It also gets a `stub` provider for tests. The stub makes a fixed 768-dimension vector from a hash of the text. A stub row records `embedding_model = 'stub'`. The HTTP modes refuse to start with the stub provider unless `OPEN_BRAIN_TEST=1` is set. The CI workflow sets that flag. The home server does not.

### Sign-in (public door)

An external identity provider issues the tokens. The server does not issue tokens. `src/auth.ts` does these checks on each request, in this order:

1. The token is present and well formed. If not: `401`.
2. The signature is valid for the keys of the configured issuer. If not: `401`.
3. The issuer is the configured issuer. If not: `401`.
4. The audience is the public resource address of this server. If not: `401`.
5. The token is not expired. If not: `401`.
6. The subject is the one permitted subject. If not: `403`.

The issuer, the audience and the permitted subject come from the ignored `.env` file. Check 6 enforces the one-user constraint: a valid token of a different account of the same provider gets `403`.

Discovery: a Claude connector can not start a sign-in from a bare `401`. The public door does two more things, and the two need no token.

- Each `401` response has a `WWW-Authenticate` header that points to the protected resource metadata.
- The route `/.well-known/oauth-protected-resource` serves the protected resource metadata. The metadata names the resource address and the configured issuer.

The SDK auth helpers give the header and the metadata route. `src/auth.ts` gives the token verifier (the 6 checks) to the bearer-auth middleware of the SDK.

Requirements for a candidate identity provider in Phase 0b:

- It issues access tokens that are signed JWTs.
- It publishes its key set.
- The builder can set the audience of the token to the resource address of this server.
- It has a client registration method that the Claude connector accepts.

A provider with opaque access tokens is rejected. The design has no introspection path.

Fallback sign-in (Cloudflare access layer): `src/auth.ts` stays. The access layer sends a signed JWT with each request, and `src/auth.ts` does the same 6 checks on it. The issuer, the audience and the permitted subject are the values of the access layer, in the same `.env` variables. The unit tests do not change. The Phase 0b exit check applies to the fallback also: one signed-in tool call from the Claude connector. The document has no evidence yet that a connector can pass the access layer.

The probe gate is not defined for the fallback yet. An access layer answers a request with no valid sign-in before the request gets to `src/auth.ts`, and its answer can be a redirect or a `403`, not a `401`. It can also send its JWT in its own request header, not in the `Authorization` header that the SDK middleware reads. If the builder uses the fallback, the builder must write these three items into this document in Phase 0b: the request header that holds the JWT and the code that reads it, the expected result of each of the 5 probe cases at the public address, and the cases that the builder probes directly at `127.0.0.1:8788` so that the 6 checks of `src/auth.ts` are exercised. Phase 2 does not start with the fallback until the document has these three items.

### Schema changes

One new file, `migrations/001-scope-hybrid.sql`. Each statement is idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and a guarded `ADD CONSTRAINT`).

| Column | Type | Purpose |
|---|---|---|
| `scope` | `TEXT NOT NULL DEFAULT 'general'`, with a `CHECK` that permits only `house`, `work`, `general` | Search filters on it. |
| `embedding_model` | `TEXT` | Records the model of each row for a later change of model. |
| `content_tsv` | `tsvector`, generated from `content` with the `simple` configuration | Full-text search. |
| `superseded_by` | `UUID` | Points from an old fact to the fact that replaced it. |

A GIN index goes on `content_tsv`.

### Existing data

The home server starts with an empty database. The builder has no `open_brain` database today: the clone has no `.env` file and the server has not run. No rows move.

For a different user of the fork who has rows from before the migration: those rows get `scope = 'general'` and `embedding_model = NULL`. `NULL` means "the model that the schema file names".

### Scope behavior

- `capture_thought`: `scope` is required. The tool schema permits only `house`, `work` and `general`.
- `search_brain`: `scope` is required. The tool schema permits `house`, `work`, `general` and `all`.
- `house`, `work` and `general` each return only rows of that scope. `scope: house` does not return `general` rows.
- `all` returns rows of each scope. The client must ask for it by name, so a search can not mix scopes by accident.
- A call without `scope`, or with a different value, fails schema validation before a query runs.
- `list_recent` gets the same required `scope` parameter with the same rules.
- Each tool description has one line of guidance: "Use `house` for home facts and `work` for project facts. Use `all` only when the user asks across topics."
- The required `scope` changes the tools for clients that use them today. The builder updates the capture instructions of each client (for example the memory instructions of Claude Code) when Phase 1 goes live.

### Hybrid search

`search_brain` makes two candidate lists and merges them.

Tokens: the server makes two sets of tokens from the query.

- Part tokens, for the substring match. The server splits the query on white space. It removes from the start and the end of each piece each character that is not a letter or a digit. It keeps the characters inside the piece, so a hyphen, a slash or a period in a part number stays. A piece is a part token if it contains a digit and has a minimum of 3 characters. The minimum stops a token such as `1` from a match with almost each row. Example: `What size is 20x25x1?` gives the part token `20x25x1`.
- Word tokens, for the full-text match. The server splits the query on each character that is not a letter or a digit, and makes the pieces lowercase. Each word token has only letters and digits, so it is safe in a `tsquery` with no escape. Example: `what's` gives `what` and `s`.

1. Vector list: the 20 rows with the smallest cosine distance to the query embedding. This is the query that exists today, with the scope filter added.
2. Text list: up to 20 rows that match one of two conditions.
   - Substring match: a row matches if `content` contains a part token (`ILIKE`, with `%` and `_` escaped). This condition finds part numbers with a hyphen or a slash, which the text parser splits.
   - Full-text match: the server joins the word tokens with OR and makes the `tsquery` with `to_tsquery('simple', ...)`. A row matches if `content_tsv @@` that query. OR is necessary because a long question that requires all words finds no row. If the query has no word token, the server does not run the full-text match.
   - Order of the text list: substring matches first, then full-text matches by `ts_rank`. Among substring matches, the row that matches the longest part token is first, then the newest row.
3. Merge: reciprocal rank fusion with the constant 60. The score of a row is the sum of `1 / (60 + rank)` over the lists that contain it.
4. Final order: each row with a substring match goes before each row without one. In each of the two groups, the fusion score gives the order. The server returns the top `limit` rows. This rule makes an exact part number the first result for all vector ranks.

`search_brain` has no similarity threshold today, and this design adds none.

The design does not assume that the `simple` configuration keeps `20x25x1` whole. The substring match covers that case, and the tests prove it.

### Tool changes

- `capture_thought`: new required `scope`. New optional `supersedes` (id of an old thought), on the private door only. With `supersedes`, the insert and the invalidation of the old row occur in one transaction.
- Reason for `supersedes` in the first version: a house fact changes. A new furnace takes a different filter, and the old size must not stay in the results.
- A superseded row is invalid. Searches exclude it by the rule that exists today (`invalidated_at IS NULL`). `superseded_by` is only a link for history.
- The public `capture_thought` (Phase 3) has no `supersedes` parameter. The public door can add a fact. It can not invalidate or replace a fact. A public call that sends `supersedes` is rejected with a clear message, and no fact is stored.
- `search_brain` and `list_recent`: new required `scope`.
- `invalidate_thought`: stays on the private door only, in all phases.

### Deployment

A Docker Compose file in the repository starts three services: `pgvector/pgvector` Postgres, Ollama, and the `open_brain` server. All secrets and addresses come from an ignored `.env` file. `.env.example` shows the variable names with placeholder values.

After the first start, the builder runs `docker compose exec ollama ollama pull nomic-embed-text` one time. The model stays in a named volume. The README documents this step.

Backup: a nightly `pg_dump` writes to a directory on the home server. A weekly job copies the newest dump to the PC of the builder over the tailnet. No dump goes to a cloud destination. If the builder adds a cloud destination later, the dump must be encrypted before it leaves the home server.

## Tests

In CI, with the service container and the stub embedder:

- Tool set: the public server registers 3 tools in Phase 2 and 4 tools in Phase 3. The private server registers 5.
- Public capture: the Phase 3 public `capture_thought` schema has no `supersedes`. A call that sends `supersedes` is rejected, stores no fact and does not invalidate a row.
- Hybrid search: a stored part number is the first result for the part number alone, for the part number in a full question, and for a part number with a hyphen. Each of these tests has a minimum of 3 competitor rows that share common words with the question.
- Tokens: a question with an apostrophe and a question mark (`What's the size of 20x25x1?`) gives no error and returns the correct row first. A query with no letter and no digit gives no error.
- Discovery: a `401` from the public door has the `WWW-Authenticate` header, and the metadata route names the configured issuer with no token.
- Scope: `scope: work` does not return a `house` row. `scope: house` does not return a `general` row. `scope: all` returns each scope. A search without `scope` is rejected. A capture with a value outside the list is rejected.
- Supersede (private door): after a capture with `supersedes`, the old row is invalid and `superseded_by` points to the new row. If the insert fails, the old row stays valid.
- Migration: a second run of `001-scope-hybrid.sql` makes no change and gives no error.
- Sign-in unit tests: `src/auth.ts` gives the correct status for each of the 6 checks, with tokens that the test signs.

On the home server:

- Probe script: calls each tool on the public door in 5 cases: no token, malformed token, expired token, wrong audience, wrong subject. The first four must get `401`. Wrong subject must get `403`. All 5 must pass before Phase 3 starts.
- Source of the probe tokens. The probe does not sign tokens, because a token that the probe signs fails at the signature check and does not exercise the later checks. Expired: a real token that the builder saved and that is past its expiry. Wrong audience: a token that the provider issues for a second resource address. Wrong subject: a token of a second account of the provider. Malformed: a fixed string.
- If the selected provider can not give one of these tokens, the builder records that in Phase 0b. The unit tests then cover that case, and the Phase 3 gate lists it as "unit test only", not as passed.
- The probe reads its tokens from an ignored file on the home server. No token goes into git. After the provider changes its keys, the builder saves a new expired token, because the old one then fails at the signature check.
- Network check: see Network.
